## Register it

A surface runs inside a studio; it is not a server of its own. **This project is
yours** — it stays in your repository and the studio reads it from there. You do
not copy anything into the SDK.

1. Keep this directory (or move it) wherever you like in your own repo, and put
   your `surfaces.json` beside the page:

   ```
   surfaces/
     surfaces.json      the row below, in a { "surfaces": [ … ] } array
     {{ID}}.html        this project's surface page
   ```

   ```json
   {{ROW_INLINE}}
   ```

2. Point the runtime at that directory:

   ```sh
   node <studio>/app/serve-studio.mjs --surfaces ./surfaces
   # or
   OPENRIG_STUDIO_SURFACES=./surfaces node <studio>/app/serve-studio.mjs
   ```

Then reload the shell. `{{LABEL}}` appears on the rail.

**Do not copy your surface into the studio's `app/surfaces/`.** If you installed
the SDK as a dependency that directory is inside `node_modules` — gitignored,
destroyed by `npm ci`, and carried by any copy of the tree, so a copied
deployment can serve a healthy manifest with the wrong surfaces. Surfaces you
own belong in your repository. See `contract/manifest.md` →
*Registering surfaces as a consumer*.

The shell reads the manifest **once at load**, so an already-open tab will not
show a newly added row until you reload it. The runtime re-validates the
manifest live — check `GET /api/contract` to see whether your row was accepted.

## Run it

Start the studio runtime (from the studio directory):

```sh
node app/serve-studio.mjs
```

Open <http://127.0.0.1:8890/> and pick **{{LABEL}}** from the rail.

If your row does not appear, the reason is spelled out in
`GET /api/contract` → `manifest.errors[]`. Validation is warn-first: a bad row
is excluded and named, and the runtime keeps serving.

## What this skeleton already does

- Checks `GET /api/contract` at boot and refuses to run against a runtime that
  cannot serve it — visibly, not silently.
- Reads `GET /api/factory/state` and renders it.
- Subscribes to `GET /api/events` and re-fetches on any signal, with a
  15-second polling fallback when the stream drops or reports `degraded`.
- Opens the agent sidebar via the `open-agent` shell message.

It uses **only stable-classified** contract items. Nothing marked
*provisional* or *runtime-internal* appears in the generated code.

## The three agent primitives

This is what makes a studio surface different from a web page. All three are
opt-in, and **two of them are already wired into the page you just generated.**

| | read | already in `{{ID}}.html`? |
|---|---|---|
| **stay fresh** without losing the user's work — markers, DATA vs CODE, state that survives a reload | `contract/change-signal.md` | **yes** — `watchSignal`, plus the degraded banner |
| **an agent sees what the user is looking at** — the focus record, and addressing state in the URL | `contract/focus.md` | no — a few lines, and the highest-value thing to add |
| **an agent operates this surface** — it posts an op, your page follows | `contract/drive.md` | **yes** — `driveSurface`, handling `say` / `refresh` / `reload` |

The drive adoption near the bottom of the page is where you add your own ops. An
op is whatever *your* surface understands; the runtime never interprets it. Handle
only what you can actually honour — a surface that accepts an op it does not
perform reports success for something that did not happen.

Try it against the running studio:

```sh
curl -X POST http://127.0.0.1:8890/api/drive \
  -H 'content-type: application/json' \
  -d '{"say":"driven from a terminal","refresh":true}'
```

Reporting focus is the one you add yourself — it is what lets an agent answer
"what am I looking at?" rather than guess. See `contract/focus.md`.

In `{{ID}}.html`, replace the body of `render()` with whatever your surface is
for. The boot check, the change-signal loop and the failure handling around it
are already correct — a normal surface should not need to change them.

A live runtime self-describes at `GET /api/contract`; that is the fastest way
to see which capabilities you actually have.
